## 1. プロダクト概要

### 1.1 コンセプト
AIを利用した小説執筆支援ツール。AIの役割は**執筆者ではなく「編集者」であり、執筆者のための「スマートな外部記憶装置」**である。

- AIは本文を書かない(AI本文執筆は将来対応。ただしアーキテクチャ上の拡張余地は残す)
- **生成との境界(v0.4追加)**: AIの出力は案・要約・質問・指摘・ブレスト素材などの**メタテキストに限る**。本アプリはAI出力を原稿ファイル(manuscript/)へ直接挿入・自動書き込みする機能を持たない(C-01解禁まで)。生成物(会話例・シーン案等)は ideas/ 等に保存し、原稿へ移すのは常に人間の手で行う
- AIの4つの役割:
  1. アイデア出しの補助(プロット・キャラクター・世界観設定)
  2. 設定管理(外部記憶)
  3. 誤字脱字チェック
  4. レビューと改善提案

### 1.2 対象ユーザー・言語
- 第一の利用者は開発者自身(日本語での小説執筆)。将来的な一般公開は未決(→Q-5)
- 日本語第一。UI・校正・AI応答すべて日本語を基準とする

### 1.3 市場での位置づけ(調査結果より)
- 「日本語 × 生成しない編集者AI」は空白地帯(英語圏の先行例: Marlowe, Fictionary, ProWritingAid)
- 「設定DBと校正・レビューの連携」はどの既存ツールにもない差別化の核
- 詳細は調査レポート§5.1参照

## 2. 基本方針(2026-07-25 追加決定の4項目)

### P-1: アイデア出し補助の対象拡張
アイデア出しの対象をストーリープロットに限定せず、**キャラクター作成・世界観設定作り**にも用いる。
→ M-03に反映。プロット/キャラクター/世界観の3系統それぞれに支援フローを設ける。

### P-2: ローカルLLM先行(テスト時のAPIコスト節約)
テスト環境でのAPIコストを節約するため、**OpenAI互換APIへの対応を先行**させ、現環境で使用可能な**LM Studio**を第一の検証環境とする。
→ M-07およびT-01〜T-07に反映。副次効果として、接続先を差し替えるだけでクラウド(OpenAI、OpenRouter経由の各社モデル等)へ移行できる(BYOK相当が最初から実現される)。

**参考実装(2026-07-25追加)**: `C:\claude\uggg`(Tauri 2製)に OpenAI互換クライアント(LM Studio/Ollama対応・寛容JSONパース)、keyringによるAPIキー管理、コスト集計が実装済みであり、これを参考・流用する。評価詳細と追加実装が必要な項目は [04-design.md](04-design.md) §5 を参照。

### P-3: オンボーディングの内蔵
本アプリは高機能性ゆえに、セットアップ・学習コストを抑制しても限界があり、実際には高くなることが想定される。そのため**チュートリアルやFAQの実装**を検討する。実装が難しい場合は**チュートリアル動画の作成**を代案とする。
→ M-08(最小オンボーディング)、S-07(本格チュートリアル・FAQ)に反映。

### P-4: UI/UXを最重要とする
機能が充実していても、アプリのUI/UXが最重要である。デファクトスタンダードとなっているアプリはこの面が優れていると想定されるため、**設計時の参考にする**。
→ §5(UI/UX設計原則)に反映。デザイン工程では調査済みツール(Nola、Dabble、Scrivener、Sudowrite、Novelcrafter等)のUIを具体的に参照する。

### P-5: 小説データは人間が直接編集できる形式で保持する(2026-07-25追加)
ユーザーの小説に関連するデータ(原稿・設定・プロット等)は、本アプリやAIだけでなく、**人間がテキストエディタ等で直接読み書きできる形式**で保持する。これを実現するため、適切な階層構造・ファイル形式等を検討する(例: Open Knowledge Format の採用)。
→ 設計検討は [03-data-format.md](03-data-format.md)(ファイルを正本とし、Markdown+YAMLフロントマター、codexはOKF互換を軸に検討)。要件面では N-02 を強化し、T-08(外部編集への耐性)を追加。

### P-6: 個人利用およびOSSリリースを目指す(2026-07-26追加)
本アプリは**開発者自身の利用**と、将来的な**OSSとしての公開**を目標とする。**販売・商用提供は考慮しない**。
→ Q-5(配布・公開の展望)を解決。影響: ライセンス選定が必要 / 収益化・課金・利用統計の送信は一切設けない / 他者が使う前提でM-08(オンボーディング)の重要度が上がる / クラウドAPIの費用最適化(S-08)は「他人に請求が行く」性質の問題ではなくなり、優先度は下がる。

### P-7: ローカルLLMを推奨環境とする(2026-07-26追加、P-2の格上げ)
ピカレスク、ハードボイルド、ロマン・ノワールなど、**犯罪・暴力の描写が本質的に必要なジャンル**がある。こうした題材を扱えることを前提に、**非検閲モデルを選べるローカルLLMを推奨環境**とする。P-2は当初「テスト時のAPIコスト節約」を理由にローカルを先行させたが、本番の推奨環境へ格上げする。クラウド接続はOpenAI互換のまま維持し、ユーザーの選択肢として残す。

#### 検閲の影響範囲(2026-07-26 実測により限定)

当初は「クラウドの主要モデルはこの題材を扱えない」と想定していたが、**過激な犯罪・暴力・性描写を含むテストデータでの実測により、この想定は限定的にしか正しくないと判明した**。

| 用途 | 検閲の影響 | 実測 |
|---|---|---|
| **非生成**(M-04 誤字脱字 / M-09 設定抽出) | **ほとんど受けない** | OpenAI GPT-OSS-120B・ChatGPT・Grok のいずれも問題なく動作。**Geminiのみ拒否** |
| **生成寄り**(M-03 アイデア出し、将来の C-01 本文執筆) | **受ける** | 犯罪描写を含む場面の展開案で、**検閲ありモデルは返答なし。非検閲モデルは動作**。用途による差を実測で確認 |

**検閲は「有害な内容を生成すること」に強く働き、「与えられた文章を分析・変換すること」には働きにくい。** 誤字脱字チェックや固有名詞抽出は後者にあたるため、検閲ありのモデルでも通る。

→ **したがって非検閲モデルの優位は生成用途に限定される。** 非生成用途では**検閲の有無よりモデルの特性と性能が重要**である。
→ ただしP-7(ローカル推奨)自体は維持する。根拠は次のとおり:
  1. 生成用途(M-03、将来のC-01)での自由度 — ここは依然として非検閲の優位が大きい
  2. **Geminiのように拒否するモデルが実在する**。題材によって使えないモデルがあるという事実は変わらない
  3. 原稿を外部へ出さない(N-03)
  4. 費用ゼロ・オフラインで動く
→ **注意すべき別の失敗形**: レビュー(M-05)では、拒否ではなく**道徳的な注釈や説教が混入する**ことがありうる。これは「動かない」ではなく「編集者として使えない出力になる」問題であり、拒否とは別に検証する必要がある([05-roadmap.md](05-roadmap.md) §5.9-B)。
→ 副次的な効果: ローカル既定なら原稿が外部へ出ないため N-03 の懸念が大幅に減る。これはP-8の実現可能性に直結する(下記)。

### P-8: ツール自体の作業負荷を最小にする(2026-07-26追加)
本アプリは**小説執筆に専念するための道具**であり、ツールの操作や認知に負荷がかかっては本末転倒である。
**目指す状態: 「ツールが自動でシーン分けや設定抽出を行い、執筆者は書くだけ」**。

- 執筆者に「実行ボタンを押す」ことを要求する機能は、可能な限り自動化の対象とする
- ただし**AIは非破壊(U-06)を崩さない**。自動化するのは「気づくこと」であって「決めること」ではない。採否は常に執筆者が持つ
- 自動化は**通知や割り込みを増やさない形**で行う(執筆中に候補が飛び出すのは負荷の増加であって削減ではない)

→ この方針により、第3回レビューで撤回した「保存時のバックグラウンド処理」を**再検討してよい状態になった**。理由は [06-decision-log.md](06-decision-log.md) §6 に記録する(撤回理由のうち費用とプライバシーがP-7で消え、残るのはノイズと計算資源のみ)。
→ 新規の検討事項として**シーンの自動分割**が加わる(現在は執筆者が手でファイルを分けている)。

## 3. 機能要件

**依存関係と実装マイルストーン(v0.4追加)**: M-01(原稿)・M-07(AI接続)・M-02(設定DB)が基盤。M-04/M-05/M-09はM-02に依存し、S-02はM-04-02とprogressionデータに依存する。実装順の推奨は **M1: M-01+M-02+M-07(+M-08最小)** → **M2: M-04+M-09** → **M3: M-05+M-03** とする。**MVP定義・マイルストーン・V1/V1.5境界の詳細は [05-roadmap.md](05-roadmap.md) に集約する(v0.5)**。

**v0.6の注記**: 第3回レビューは「Mustが多く、MVPで検証していない仮説の上に構造を積みすぎている」と指摘した。これを受けM-06を降格し実装前の抽象化を撤回したが、**AIの4役割(アイデア出し/設定管理/誤字脱字/レビュー)をV1の要求に含めるかどうかはプロダクト定義そのもの**であり、要件の取捨ではなくQ-7としてユーザー判断に委ねる。現時点では4役割を維持し、検証順序で立ち上げる方針とする。

### 3.1 Must(初期リリースの中核)

#### M-01 プロジェクト・原稿管理
- 複数プロジェクト(作品)の管理
- 章・シーンの階層構造。ドラッグ&ドロップでの並べ替え(構成変更が本文と自動連動すること — Scrivener/Plottrの手動同期を避ける)
- 文字数カウント(シーン/章/全体)、執筆進捗の把握
- プレーンテキスト/Markdownでのエクスポート(データの人質化をしない)
- **保存時バックアップ(v0.6でM-06から移設)**: 保存のたびに1世代のバックアップコピーを残す(履歴UIは持たない)。ドッグフーディング中の「壊れるのが怖くて書き進められない」を防ぐ最小限の安全網
- **単一ファイル内検索(v0.6追加)**: 開いているファイル内のインクリメンタル検索(全文検索=FTS5は後続)。1万字執筆時に「あのシーンどこだっけ」で詰まらないための最小機能
- **表示の補助(2026-07-26 ドッグフーディングの指摘で追加)**: 本文と参照ビューに**行番号**を表示できること。本文には**横ルーラー**と、**任意の字数での折り返し**(20/30/40/42/50字・カスタム・右端)を設定できること。日本語の原稿は字詰めを意識して書かれるため、全角1文字の送り幅を実測して桁の基準とする。設定は記憶する
- **項目の管理操作(2026-07-26 ドッグフーディングの指摘で追加)**: ツリー上でファイル・フォルダーの作成/改名/複製/削除ができること。**削除は不可逆にしない** — プロジェクト内のゴミ箱へ退避し、確認ダイアログで復元先を案内する(D-1「ファイルが正」の帰結として、アプリが原稿を永久に失う操作を持たない)。改名時はプロジェクト内のリンクを追随させる([03-data-format.md](03-data-format.md) §5-6)
- **自動保存(2026-07-26 ドッグフーディングの指摘で追加)**: 入力が止まった時・ファイル切替時・ウィンドウのフォーカスを失った時・ウィンドウを閉じる時に自動保存する。**保存操作を執筆者に要求しない**(明示保存Ctrl+Sは残す)。保存前バックアップと併せて「編集内容が消えない」ことを保証する

#### M-02 設定管理DB(外部記憶の本体)
- エントリ種別: キャラクター/場所/アイテム/用語/自由メモを推奨既定とし、**ユーザー定義種別を追加できる開放語彙**とする(組織・事件・魔法体系等を自由に追加。種別のハードコード増殖はしない)
- 各エントリ: 名前、**別名(あだ名・旧名・表記違い)**、説明、タグ、画像(任意)
- エントリ間の関係(from→to の方向+種別ラベル。例: 親子、所属、敵対)
- **本文中の言及検出**: 原稿内にエントリ名・別名が登場する箇所の自動検出・一覧・ジャンプ(文字列一致+別名辞書。**位置は保存せずオンデマンド算出**=[04-design.md](04-design.md) §6.4)
- 全文検索
- **エントリ作成テンプレート(2026-07-26 ユーザー要望で追加)**: 新規作成時に記入項目の雛形を提示する(キャラクターなら性別・年齢・性格・話し方・物語での役割など)。**テンプレートはジャンル別**に用意し、**ユーザーが自由に編集・追加できる**こと。実装形態は設定フォルダ内の普通のMarkdownファイルとし、ジャンル追加はフォルダ作成だけで済むようにする(記入負担を下げつつ、フロントマターの解釈規約は崩さない=構造化項目は本文の見出し・箇条書きに置く)
- **V1スコープ(v0.4、v1.0改訂)**: 名前・別名・説明・言及検出・作成テンプレートまで。タグ・関係の編集UI・画像・時系列変化(progression)はV1.5以降。**V1でアプリが解釈するフロントマターは type/title/aliases/description の4つに絞り、それ以外は未知フィールドとして無改変で保持する**(手書きの内容を壊さない。[03-data-format.md](03-data-format.md) §4.1)
- 参考実装: Novelcrafter Codex(調査レポート§4パターン③)

#### M-03 アイデア出し補助(P-1反映: 3系統)
- **プロット**: 対話型ブレインストーミング、What if提案、プロット方法論テンプレート(起承転結・三幕構成・Save the Cat等)を起点にした展開支援
- **キャラクター**: 質問による深掘り(動機・欠点・恐れ・口調など editor 的インタビュー)、既存キャラ一覧との重複・役割被りの指摘
- **世界観設定**: ディテールの提案、設定の抜け・未定義箇所の質問(「この魔法の代償は?」)、既存設定との整合質問
- いずれも結果をワンタップでM-02の設定DBエントリ/プロットカードとして保存できること(チャットで完結させず資産化する)
- **V1スコープ(v0.4)**: 対話UI+方法論テンプレート起点+結果保存に絞る(3系統それぞれの専用ウィザードUIは段階導入)

#### M-04 誤字脱字チェック・校正(v0.4でサブ分解)
- M-04-01 誤字脱字・変換ミス・衍字/脱字の検出(LLMベース)。**PoC#7(2026-07-26)の実測によりローカルLLMで実用可と確定**。ただし長文をまとめて渡すと検知率が落ちるため**3000字ごとに分割して検査する**こと、実用には30 tok/s程度の速度が要ることを前提とする(詳細は [04-design.md](04-design.md) §7-7・§8)
- M-04-02 **設定DB連携の固有名詞チェック**: キャラ名・地名等の表記ゆれ(「架純」vs「佳純」)を設定DBの正規名+別名と機械照合(LLMは補助)で検出 — 既存校正ツールとの差別化点であり、**整合性チェック(S-02)のV1最小形**
- M-04-03 非破壊提示: 指摘一覧+該当箇所ハイライト。位置は保存せず、**V1は「実行時の本文ハッシュで結果の鮮度を管理し、本文が変わったら『古い結果』として再実行を促す」方式**とする(個別指摘の永続再アンカーはV1では実装しない。v0.6で簡素化=[04-design.md](04-design.md) §6.4)
- M-04-04 小説文体への配慮: 会話文・意図的な崩し表現への誤検出を抑える(小説文体前提のプロンプト・辞書設計)

#### M-05 AIレビュー・改善提案
- 対象範囲を選択してレビュー: シーン単位/章単位/作品全体
- **観点タクソノミ(v0.4で固定)**: ①文章品質(文体・冗長・読みやすさ) ②構成・テンポ(場面の要否・順序・ペース配分) ③キャラクター(一貫性・動機・アーク) ④設定整合性(codexとの矛盾) ⑤読者視点(感想・引き・離脱リスク)。プロンプトはこの分類単位で管理し、勝手に増減させない
- **全体レビュー=構成編集を明示機能とする**: 「この章は不要では」「主人公の動機が弱い」など作品全体への編集者的講評(編集者コンセプトの中核。Fictionary/Marlowe型)
- 出力形式: 引用付きコメント(M-04-03と同じ鮮度管理方式)+全体講評。**執筆モードと分離した「レビューモード」で表示**し(U-10)、1件ずつの採否に加えて一括適用/棄却UIを備える
- レビュー時のコンテキスト構築(設定DB・プロットの供給)は [04-design.md](04-design.md) §6.2 に従う
- **V1スコープ(v0.5追加、v0.6改訂)**: V1はシーン/章(〜数章)のレビューまで。**作品全体レビューはV1.5**とし、方式の候補は「章レビュー結果の統合」([05-roadmap.md](05-roadmap.md) §5.2の将来メモ。処理時間・コスト爆発の回避)。実行前に規模・概算コストを提示する(S-08連動)。**要約のバックグラウンド自動生成はv0.6で撤回**(保存ごとのAI処理・原稿の自動送信=N-03違反を避ける)
- 参考体系: Fictionaryの38ストーリー要素、Marloweの構造分析(調査レポート§2-E)

#### M-06 版管理 → **v0.6でShould(S-11)へ降格**
- 降格理由: 正本がプレーンテキストであるため、git/OneDrive/ファイル履歴等の既存手段で代替でき、第一利用者が開発者自身であることを踏まえると初期リリースの必須要件ではない(外部レビューR1-7)
- **V1で持つのは「保存時に1世代のバックアップコピーを取る」だけ**(M-01に含める)。履歴一覧・差分表示・復元UIは必要性を実感してから(S-11)

#### M-07 AI接続基盤(P-2反映)
- OpenAI互換API(`/v1/chat/completions`)を標準インターフェースとする
- 接続設定: Base URL/APIキー/モデル名を設定画面で変更可能。プリセット: **LM Studio(`http://localhost:1234/v1`)**/OpenAI/その他OpenAI互換(OpenRouter、Ollama等)
- ストリーミング応答対応(体感速度はUXに直結)
- 接続テスト機能(疎通・モデル一覧取得)
- **AI未接続でもアプリの非AI機能(M-01/M-02)は完全動作すること**
- 認証情報(APIキー)はOS資格情報ストアに保存し平文で持たない
- 接続失敗・タイムアウトはユーザーに分かる形で通知する
- **v0.6で撤回**: 機能別モデル割当(プロファイル)機構は要件から外す。V1は「ユーザーが設定した1つの接続先を全機能で使う」。機能ごとの推奨モデルは参考情報として [04-design.md](04-design.md) §8 に置く

#### M-08 最小オンボーディング(P-3反映)

**FAQ・チュートリアルに必ず含める項目(2026-07-26追加)** — 実装時に漏らさないこと。
いずれも「知らないと結果を誤解する」性質のもので、単なる便利情報ではない。

- **① 題材に応じたモデル選定(検閲の有無)**: **暴力・犯罪・性描写を伴う内容を扱う場合は非検閲モデルを推奨する**旨を明示する。ここは用途によって影響が違うことまで説明が必要:
  - **校正・設定抽出(与えられた文章を分析する用途)は、検閲ありのモデルでも通る**。検閲を理由に避ける必要はない
  - **展開案などの「書かせる」依頼は、検閲ありのモデルでは拒否される**(実測で確認)。ここが非検閲モデルを選ぶ理由になる
  - **モデル差がある**。Geminiは校正すら拒否した
  - **失敗の形が分かりにくい**: エラーではなく**応答が1文字も返らない**。アプリ側でも検出して伝えるが、FAQでも「無反応に見えたら検閲を疑う」と説明する
  - 根拠: [04-design.md](04-design.md) §8.1、[02-requirements.md](02-requirements.md) P-7
- **② LLMの動作設定**: 接続設定だけでなく**モデル選定とLM Studioの設定**を盛り込む。設定を誤ると「誤字なし」と誤報告されかねない。最低限、⑴30 tok/s程度は必要 ⑵コンテキスト長を増やすときは並列数を1に下げる(KVキャッシュが並列数の分だけ増える) ⑶校正の分割字数はコンテキスト長に合わせる、を扱う(根拠は [04-design.md](04-design.md) §7.1・§7.2)
- サンプルプロジェクト同梱(機能を触りながら学べる。Fictionaryのデモ原稿方式)
- 空状態(empty state)ガイダンス: 各画面の初期状態に「何をする場所か・最初の一歩」を表示
- LM Studio接続のセットアップガイド(初回のつまずき筆頭になると想定されるため、画面付き手順を内蔵)

#### M-09 本文からの設定自動抽出(提案型)(v0.4でS-01から昇格)
- 原稿を解析し、未登録のキャラクター・場所・用語をcodexへの追加**候補として提案**する(自動登録はしない=U-06の非破壊原則)。「書けば書くほど外部記憶が勝手に育つ」導線
- 昇格理由: U-01(ゼロ設定で書き始める)と、設定DBを前提とする差別化機能(M-02/M-04-02/M-05)を両立させる唯一の経路。これがないと初期ユーザーはコールドスタート問題により本アプリの価値を体験できない([06-decision-log.md](06-decision-log.md) §3)
- **V1スコープ(v0.5改訂)**: **手動実行のみ**(ユーザーが対象範囲を指定してボタンで抽出。バックグラウンドの常時自動抽出はしない)。検出はエンティティ名+種別+一行説明に絞り、固有名詞らしさのフィルタ(一般名詞・「黒い服の男」等のモブ表現の除外)をRust側に持つ。候補の一括棄却UIを備える — ローカルLLMのNER精度に起因する「候補ノイズが執筆を阻害する」事態の回避(外部レビューR1-2)

## 4. AI接続の技術要件(P-2詳細)

**本節の位置づけ(v0.6追加)**: 純粋な要求は「①AI接続先を設定できる ②ストリーミング応答を表示できる ③認証情報を安全に保持する ④接続失敗をユーザーへ通知する ⑤AI未接続でも非AI機能が動く」の5点である。以下のT-01〜T-09は**現時点の技術選定([04-design.md](04-design.md))に基づく実現手段の制約**であり、選定が変われば要求ではなく本節を改訂する。

| ID | 要件 |
|---|---|
| T-01 | OpenAI互換APIを唯一の必須インターフェースとする。ベンダーSDKへの直接依存を避け、Base URL差し替えで LM Studio/OpenAI/OpenRouter/Ollama 等に接続できる抽象化層を設ける |
| T-02 | 第一検証環境は LM Studio(既定 `http://localhost:1234/v1`)。開発・テストのAPIコストをゼロにする |
| T-03 | ストリーミング(SSE)対応。長い講評の逐次表示 |
| T-04 | 構造化出力: LM Studioは `response_format.json_schema` によるスキーマ強制に対応(llama.cppの文法サンプリングでトークンレベル強制)。校正指摘・レビューコメントの機械可読化に利用する。ただし**モデル・プロバイダによる対応差を前提に、寛容なパース+再試行のフォールバック**を必ず実装する。さらに**構造化出力を使わないプレーンテキスト+規約プロンプト+寛容パースの軽量経路**を機能ごとに用意し、用意する(v0.4、[04-design.md](04-design.md) §6.3。経路はコード上で機能ごとに指定し、設定による動的切替機構は作らない=v0.6) |
| T-05 | モデル能力差への耐性: コンテキスト長の設定/自動検出、長文の分割戦略(章単位分割→統合)。ローカル小型モデルでの品質劣化を想定し、機能ごとに「必要最小限の文脈だけを渡す」設計(調査レポート§4のLorebook的発想) |
| T-06 | AI応答の全ログ保存(検証・プロンプト改善・再現に必須。テスト段階では特に重要) |
| T-07 | 校正(M-04)はLLM一発に依存せず、将来的にルールベース(textlint等)との併用を可能にする構成を許容 |
| T-08 | 外部編集への耐性(P-5、**v0.6で縮小**): 「外部編集できる」ことと「同時編集を安全に統合できる」ことは別要件であり、V1は前者のみを扱う。具体的には**アプリにフォーカスが戻った時点でファイル更新時刻を確認し、外部変更があれば再読み込みを促す**。アプリ側に未保存変更がある場合は「別名保存」か「破棄」の二択とし、自動マージはしない。リアルタイム監視・競合の自動退避・低優先の全体再索引はV1では実装しない。形式の崩れは寛容にパースし警告表示する。詳細は [03-data-format.md](03-data-format.md) §5 |
| T-09 | AI連携の実装方針(v0.4追加、**v0.6で縮小**): AI機能は**機能ごとに独立実装**し、同じコードが2回以上必要になった時点で共通部を抽出する。V1で共通化するのは「AI送信処理」と「ファイル読み込み処理」のみ。全機能を貫く共通パイプラインは、AI機能を2つ以上実装した後に実際の重複を見て定義する。V1の実装範囲は [04-design.md](04-design.md) §6 |
| ~~T-10~~ | **v0.6で撤回**: 汎用AI実行エンジン(プロンプトバージョン管理・モデル自動解決・入力ハッシュキャッシュ・レート制御・複数モデル多重化)は実装前の過剰な抽象化であり要件から削除する。V1は `send/stream/cancel` の薄いクライアント+ログ記録のみ([04-design.md](04-design.md) §6.1)。特にキャッシュは温度・モデル・プロンプト・接続先が異なれば結果の意味が変わるためキー設計が破綻しやすく、V1では持たない(外部レビューR1-2/R2-①) |

**テスト用ローカルモデルの候補(調査時点の外部情報)**: 日本語品質と構造化出力の観点で Qwen3.5/3.6系、Gemma 3/4系が有力とされる。実機のVRAMに応じて量子化版を選定し、本アプリの各機能(ブレスト/校正/レビュー)で比較評価する。

## 5. UI/UX設計原則(P-4詳細)

デファクトスタンダードのツール群から抽出した原則。デザイン工程での判断基準とする。

| ID | 原則 | 出典(参考ツール) |
|---|---|---|
| U-01 | ゼロ設定で書き始められる。AI設定・DB構築を済ませなくても執筆を開始できる | Novelcrafterの反面教師(セットアップの重さが最大の不満点)、Nolaの手軽さ |
| U-02 | 段階的開示: 初心者には基本機能のみ見せ、使い込むほど高度な機能が現れる | World Anvilの反面教師(機能の壁) |
| U-03 | 執筆画面は没入優先(distraction-free)。AI・DBパネルは呼んだ時だけ現れる | Scrivener/Dabble/Ulysses |
| U-04 | 執筆と参照の同居: 本文を書きながら設定DBをサイドパネルで参照・編集できる。ツール切替による集中断絶を作らない | Hakogakiの設計思想、Novelcrafterのサイドバー |

| U-06 | AIは非破壊: AIの指摘・提案は必ずコメント/差分/提案の形で提示し、本文・設定DBを勝手に書き換えない(採否は常にユーザー) | 本プロダクトの「編集者」コンセプトの体現 |
| U-07 | 日本語執筆の作法を尊重: 字下げ、全角記号、三点リーダ、ダッシュ、(将来)ルビ・縦書き | Nola/一太郎/縦式 |
| U-08 | 空状態がチュートリアルを兼ねる: 白紙画面に次の一歩を必ず提示 | M-08と連動 |
| U-09 | 待ち時間の設計: AI応答はストリーミング表示し、処理中も執筆を継続できる(ブロッキングUIにしない) | Sudowrite等のカード型非同期UI |
| U-10 | モード分離(v0.4追加): 執筆モード(没入・装飾最小)と校正・レビューモード(指摘オーバーレイ・採否UI)をフェーズとして分離し、執筆中に大量の指摘が常時重畳しない | 外部レビューR2-3B(マーカーずれ・UI渋滞の回避) |
| U-11 | 操作コスト目標(v0.4追加): 主要AI機能(校正・レビュー・ブレスト)の開始は3クリック/3秒以内、シーン切替は1クリック。設計レビューはこの値で判定する | 外部レビューR1-7(測定可能なUX基準) |
| U-12 | 画面配分はユーザーが決める(2026-07-26追加): ペインの幅は**境界のドラッグ**で変更でき、記憶される。**サイドペインは開閉できる**(常時表示を強制しない) | ドッグフーディングの指摘。U-03(没入)とU-04(参照の同居)の両立は、固定レイアウトではなくユーザーの調整に委ねる |
| U-13 | 参照は執筆を中断させない(2026-07-26追加): サイドペインはAI専用にせず、設定を**読みながら書く**ための参照ビューを持つ。本文中の設定名から直接引ける(Ctrl+クリック) | ドッグフーディングの指摘。「外部記憶装置」の体験はここに出る |

**デザイン工程の進め方**: 実装前に主要3画面(執筆画面/設定DB画面/レビュー画面)のプロトタイプを作成し、参考ツールのスクリーンショットと並べて比較検証する。開発者自身によるドッグフーディングを継続的に行う。

## 6. 非機能要件

| ID | 要件 |
|---|---|
| N-01 | パフォーマンス(**v0.6で格下げ**): **V1の判定基準は「入力が目に見えて遅延しない/シーン切替が執筆を妨げない/1万字の実プロジェクトで問題なく動く」**の3点とする。30万字・300ファイルでの数値目標(起動3秒/切替100ms/検索500ms/言及スキャン2秒)は**参考値であり未実測**。アーキテクチャを不必要に誘導しないよう、確定値はMVPの実測後に定める(一太郎の500KB問題は反面教師として意識する) |
| N-02 | データ安全: ローカル保存を基本とし、自動バックアップ、破損時復旧を備える。**保存形式そのものを人間可読なテキスト(Markdown+YAMLフロントマター)とし(P-5)、エクスポートを介さずとも外部ツールで読み書きできる状態を常態とする**。独自バイナリ形式によるロックインをしない。詳細設計は [03-data-format.md](03-data-format.md) |
| N-03 | プライバシー: ローカルLLM利用時は原稿が外部送信されないことを保証。クラウドLLM利用時は送信範囲を明示(U-05と連動)。**P-7でローカルが推奨環境になったため、既定の構成では原稿は一切外部へ出ない**。クラウドを選んだ場合のみ送信が発生することを設定画面で明示する |
| N-04 | オフライン動作: AI機能以外はオフラインで完全動作 |
| N-05 | 拡張性: AI層はプロバイダ追加・将来のAI執筆機能(C-01)に耐える抽象化。機能追加がコア(原稿・設定DB)を壊さないモジュール構成 |
| N-06 | AI品質の測定可能性(v0.4追加、**v0.6で実施時期を後退**): 誤字・矛盾を埋め込んだゴールデンテストセットで検出率・誤検知率を機械計測できること。**V1では測定基盤を作らず、M2のPoC#7で誤字10件程度の最小版から始める**。それまではAI呼び出しログ(プロンプト実体・モデル・渡した素材)を残すことで事後追跡を可能にしておく([05-roadmap.md](05-roadmap.md) §5.3) |

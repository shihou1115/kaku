## 1. 設計原則

| ID | 原則 | 理由 |
|---|---|---|
| D-1 | **ファイルが正、アプリは従**: プロジェクトフォルダ内のテキストファイル群を唯一の正本(source of truth)とし、アプリ内部のDBは検索・言及検出用の**再生成可能な索引**に限定する | アプリが消えてもデータが読める。外部編集が第一級の操作になる |
| D-2 | **1概念1ファイル、Markdown+YAMLフロントマター** | 人間可読・diff可読・AI可読を同時に満たす業界標準構成(OKF/Obsidian/静的サイト等と同型) |
| D-3 | **ファイル名・フォルダ名も人間向け**(連番+日本語名)。**V1はファイルパスを識別子として扱い**、安定ID(`id`)はリネーム追跡・相関図が必要になった時点で導入する(§4.1) | エクスプローラで開いただけで構造が分かる。IDを最初から必須にすると手書きの負担になる |
| D-4 | **原稿本文はほぼプレーンテキスト**: 構造はファイル分割とフロントマターで表現し、本文内に記法を持ち込まない(ルビ等の最小記法のみ将来検討) | 執筆者がメモ帳で開いてそのまま書ける。投稿サイトへのコピペも無加工 |
| D-5 | **外部編集への耐性**: 寛容なパース、未知フィールドの無改変保持、非破壊(勝手に上書きしない)。**変更検知はフォーカス復帰時の確認に留め、常駐監視はしない**(§5) | 「人間が直接編集できる」は「編集されてもアプリが壊れない」とセット(T-08)。ただし同時編集の統合までは引き受けない |
| D-6 | **バージョン管理親和**: UTF-8(BOMなし)、テキストのみ、安定したファイル順序。gitやファイル同期ツールにそのまま載る | バックアップの基盤。この性質があるため版管理はS-11へ降格できた |
| D-7 | **位置情報を保存しない**(v0.2追加): 言及箇所・AI指摘の文字オフセットは永続化せず、表示時にオンデマンド算出・再解決する(V1はAI指摘の結果を本文ハッシュで鮮度管理する=[04-design.md](04-design.md) §6.4)。索引が持つのは「どのファイルに何があるか」のファイル粒度まで | 外部編集(P-5)で位置は常に無効化されうるため。位置の永続化は破綻が必然 |

## 2. 先行事例の評価

| 事例 | 形式 | 学ぶ点 | 採らない点 |
|---|---|---|---|
| **Open Knowledge Format (OKF)** (Google Cloud, 2026-06発表) | Markdownファイルのディレクトリ。1ファイル=1概念。YAMLフロントマター(type/title/description/resource/tags/timestamp)。通常のMarkdownリンクで概念間を結び知識グラフを構成 | 「AIエージェントに与える知識をMarkdownで標準化する」思想が本アプリの外部記憶コンセプトと一致。設定DB(codex)の器としてほぼそのまま使える | v0.1で発展途上。小説特有の情報(別名・登場時点・POV等)は標準フィールドにない→独自拡張が必要 |
| **novelWriter** (OSS小説エディタ) | プロジェクトフォルダ+ルートのXML構造ファイル+content/以下のプレーンテキスト(メタデータヘッダ付き)+meta/のJSON | 「構造ファイル+本文ファイル+派生メタ」の3層分離。git/同期ツール前提の設計 | 本文ファイル名が英数字ID(人間には判読不能)。構造が単一XMLに集中し、手編集に不向き |
| **Obsidian vault** | Markdown+フロントマター+`[[wikilink]]` | 「フォルダをそのまま開けば知識ベース」という体験。事実上の人間可読標準。**本アプリのプロジェクトがObsidianでも開けること**は互換目標にする価値がある | アプリ専用プラグイン依存の機能は再現しない |
| **yWriter** | 単一XMLプロジェクトファイル | シーンに登場人物・場所を紐付けるデータモデル | XML一枚岩は手編集・差分に不向き |
| **Scrivener** | .scrivパッケージ(RTF+内部メタデータ) | — | バイナリ寄り独自形式は本方針の反面教師 |

## 3. 提案: プロジェクトフォルダ構成

```
<作品名>/                        ← ユーザーが任意の場所に置ける通常フォルダ
├─ project.md                   # 作品全体のメタ情報+あらすじ(フロントマター付きMarkdown)
├─ manuscript/                  # 【原稿】章フォルダ/シーンファイル
│  ├─ 01-第一章-転校生/
│  │  ├─ 01-出会い.md
│  │  └─ 02-放課後.md
│  └─ 02-第二章-文化祭/
│     └─ 01-準備.md
├─ codex/                       # 【設定DB=外部記憶】OKF準拠ゾーン。1概念1ファイル
│  ├─ characters/
│  │  ├─ 佐藤架純.md
│  │  └─ 五十嵐悠二.md
│  ├─ locations/
│  │  └─ 県立青葉高校.md
│  ├─ items/
│  ├─ terms/                    # 用語・固有名詞
│  └─ notes/                    # 自由メモ
├─ plot/                        # 【プロット】
│  ├─ outline.md                # 全体構成(起承転結/三幕など)
│  └─ cards/                    # プロットカード(1カード1ファイル)
├─ ideas/                       # 【アイデア】ブレスト結果の採用分(M-03の保存先)
├─ reviews/                     # 【AIレビュー履歴】1レビュー1ファイル(結果の資産化)
├─ exports/                     # 出力物(投稿用整形など)。アプリが生成、正本ではない
└─ .app/                        # アプリ専用領域(人間の編集対象外であることを名前で示す)
   ├─ index.sqlite              # 索引(M3のFTS5全文検索用)。【いつ消しても再生成可能】
   ├─ settings.json             # プロジェクト固有のアプリ設定
   ├─ logs/                     # AI呼び出しログ(プロンプト実体・応答・トークン数)
   ├─ backups/                  # 保存時1世代バックアップ(V1)。→§6
   └─ trash/                    # 削除したファイルの退避先(<日時>/<元のパス>)
```

要点:
- **人間が触るのは `.app/` 以外の全部**。フォルダ名は役割がそのまま分かる日本語/英語并記も検討(既定は上記)
- 章・シーンの順序は**ファイル名の連番プレフィックス**で表現(エクスプローラでも正しい順に並ぶ)。**V1に並べ替え操作は無い** — 順序を変えるのは改名(ツリーの「名前の変更」)であり、その際はプロジェクト内のリンクを書き換える(§5-6)。ドラッグ&ドロップでの並べ替え+自動採番し直しは未実装(2026-08-05 のV1リリース判定で確認)
- Windowsのファイル名禁止文字(`\/:*?"<>|`)・長パスはアプリ側でサニタイズ・警告
- codex/ の種別フォルダ配下には**自由にサブフォルダを掘ってよい**(例: `characters/主要/`、`characters/モブ/`)。type はフロントマターに書けばそれが正、省略時はフォルダ位置から推定する(v0.4)。アプリUIは種別・フォルダでグルーピング表示し、ファイル数の多さを人間に直接意識させない(大量エントリ時の管理性への対応=R2-8)

## 4. ファイル形式仕様案

### 4.1 codexエントリ(設定DB) — OKF互換+独自拡張

**V1で解釈するフィールドは最小限とする(v0.4)**。人間が手で書けることがP-5の要諦であり、10個のキーを正しく手入力させる形式はこの原則と衝突する。

```markdown
---
type: character             # 推奨5種+ユーザー定義可(開放語彙)
title: 佐藤架純
aliases: [架純, かすみん]    # 別名(M-02言及検出・M-04表記ゆれ検出に使用)
description: 主人公。県立青葉高校の二年生。
---

## 外見
黒髪ロング(第二章まで)。

## 口調
一人称は「わたし」。[五十嵐悠二](../characters/五十嵐悠二.md)の前でだけ早口になる。
```

- **手書きで必須なのは `title` のみ**。type は省略時にフォルダ位置から推定する。aliases・description は推奨(空でも動く)
- **V1で解釈しないフィールド(v0.4で除外)**: `id`(安定ID)、`tags`、`timestamp`、`importance`、`relations`、`progression`。形式としては書いてあってもよく、**アプリは未知フィールドを解釈せずそのまま保持して往復保存する**(手編集の内容を壊さない)。各フィールドは**それを使う機能を実装する時点で解釈対象に加える**(テキスト形式なので後からの追加は容易であり、「将来のために今から検証・移行の対象にする」必要はない)
  - `importance` は撤回(静的な重要度は「この場面で重要」とは別概念で、コンテキスト選抜の精度向上が保証されない=[04-design.md](04-design.md) §6.2)
  - `id` はV1ではファイルパスを識別子として扱い、必要になった時点(リネーム追跡・相関図)で導入する
- typeは推奨5種(character/location/item/term/note)+**ユーザー定義を許す開放語彙**(organization/event/magic等を自由に追加、v0.2)
- 本文はMarkdown自由記述。見出しでセクション化するとAIへの部分供給(T-05)がしやすい
- リンクは通常のMarkdown相対リンク**のみ**(OKF互換)。**`[[wikilink]]` は受け付けない**(2026-08-05 のV1リリース判定で確定、→§7未決-1)。改名時にリンクを追随させるのもMarkdown相対リンクだけである

### 4.2 原稿シーンファイル

```markdown
---
title: 出会い
status: draft               # idea/draft/revised/done(任意)
pov: 佐藤架純              # 視点キャラ(codexのtitle。任意)
synopsis: 転校初日、架純が悠二とぶつかり第一印象は最悪に。
---
　転校初日の朝は、雨だった。
　わたしは昇降口で靴を履き替えながら……
```

- **本文は素のテキスト**(段落・全角空白の字下げ・空行のみ)。Markdown記法は解釈しない(D-4)
- V1で必須なのは**フロントマターなしでも動くこと**。`title` 未記入時はファイル名を表示名とする。status/pov/synopsis は任意(V1では表示のみ)
- シーンに登場するキャラ・場所は原則**本文からの自動検出**(M-02)で賄い、フロントマターへの手動列挙は必須にしない(記入負担の最小化)。povと必要な明示だけをメタに持つ
- ルビの記法は **2026-08-04 に `｜漢字《かんじ》` で確定**(→§7未決-3)。傍点は未決のまま。
  **本文に記法が入るぶん、字を数える処理・語を切り出す処理は記法を外してから扱う**
  (文字数表示・表記ゆれ検出)。AIへ渡す本文は外さず、プロンプト側で「誤字ではない」と伝える

### 4.3 その他

| ファイル | 形式 |
|---|---|
| project.md | フロントマター(作品タイトル、ジャンル、目標文字数等)+あらすじ本文 |
| plot/outline.md | 見出し=構成単位(起/承/転/結など)。シーンへのリンクを列挙 |
| plot/cards/*.md | 1カード1ファイル(id, 順序, 対応章)+自由記述 |
| reviews/*.md | フロントマター(日時、対象範囲、観点、使用モデル)+指摘本文。**AIの出力も人間可読な資産として残す** |
| .app/settings.json | アプリ設定(JSON)。人間編集対象外だがテキストではある |

### 4.4 文字コード・改行

- UTF-8(BOMなし)で書き出し。読み込みはBOM付き・Shift_JISも受容して変換提案(既存原稿インポート=Q-4に接続)
- 改行はLFで書き出し(git親和)、読み込みはCRLF/LF両対応。ファイル単位で既存の改行コードを保持

## 5. 外部編集との共存(T-08の実現)

**方針(v0.4で縮小)**: 「外部編集できる」ことと「外部との同時編集を安全に統合できる」ことは別要件である。後者を作り込むとローカルアプリ内に小規模な同期・競合解決システムを抱えることになるため、**V1は前者だけを保証する**(外部レビューR1-6)。

V1の仕様:

1. **変更検知はフォーカス復帰時**: アプリがフォーカスを得た時点で開いているファイルの更新時刻を確認し、外部変更があれば**再読み込みを促す**(常駐のリアルタイム監視は行わない。行う場合も通知のみ)
2. **未保存変更との衝突**: アプリ側に未保存変更がある状態で外部変更を検知した場合、「別名で保存」または「破棄して再読み込み」の**二択**とする。自動マージ・自動退避スナップショットは行わない
3. **寛容なパース**: フロントマター欠落・YAML崩れは「メタなしMarkdown」として読み、エラーではなく警告表示にする。未知フィールドは解釈せずそのまま保持する(§4.1)
4. **索引の使い捨て保証と差分更新**: 起動時に mtime+サイズ比較で**変更分のみ再索引**する。全再構築は `index.sqlite` 破損時のみ
5. **索引の粒度**: 索引はファイル粒度に留め、文字オフセットは保存しない(D-7)
6. **リネームとリンクの境界**: アプリ内でのエントリ改名・ファイル移動はプロジェクト内リンクを自動書き換えする。**アプリ外での改名は自動修復しない**(リンク切れとして表示するに留める)

## 6. バックアップと版管理

**V1**: 保存時に対象ファイルを `.app/backups/` へ1世代コピーするだけ(履歴UI・差分表示は持たない)。版管理そのものはS-11へ降格済み。

**S-11(V1.5以降)を実装する場合の選択肢**:

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| (a) 世代スナップショット | 保存時/手動時に変更ファイルを `.app/snapshots/<日時>/` へコピー。差分は表示時に計算 | 実装が単純・確実。仕組みが目視で分かる | 容量効率が悪い(テキストなので実害は小さい) |
| (b) 内蔵git | gitoxide/libgit2でプロジェクトを自動コミット。UIではgitを見せない | 差分・復元・履歴が完璧。将来ユーザー自身のgit運用ともシームレス | 実装複雑。gitを知らないユーザーへの露出事故に注意 |
| (c) ユーザー任せ | 形式がgit親和なので自分でgit/同期ツール(OneDrive・ファイル履歴等)を使ってもらう | 実装ゼロ | 初心者を守れない |

**推奨**: (a)で確実に出し、必要なら(b)へ移行検討。(c)はD-6により常に併用可能であり、これが版管理を降格できた根拠。

| ~~未決-1~~ | リンク記法の既定 | **2026-08-05 決定: Markdown相対リンクのみ**(V1リリース判定で確定)。`[[ ]]` は読み込みも受け付けない。判定時にコードを当たった結果、wikilinkの処理はどこにも無く、**書いてあるだけの未実装仕様**だった。改名時のリンク追随がMarkdownリンクにしか効かない以上、受け付けるふりをすると「改名したらリンクが切れた」という壊れ方になる。必要になったら**追随の実装とセットで**入れる |

## 1. 開発原則

1. **ドキュメントより先に、動くものでドッグフーディングする**
2. **仕様策定は終了した**(2026-07-25、文書統合をもって完了)。以降のドキュメント更新は「実装で判明した事実の反映」と「本書のゲート判定記録」に限る。**紙上での設計追加は行わない** — 3回の外部レビューが共通して指摘した最大リスクは「コードを書く前に、自ら作った仕様の重圧で疲弊すること」だった
3. **伴走型 → 事後評価型の順で作る**: まず「設定管理・参照・AI相談」(ローカルLLMで成立する領域)を完成させ、「校正・レビュー」(モデル能力要求が高い領域)は後段で載せる
4. **インフラの一般化は使ってから**: 共通化・品質測定基盤は、MVPで1万字書いた後に必要性の実感を持って作る
5. **リスクは先頭で潰す**: PoC#1(エディタ×IME)をWeek 1に実施。ここの失敗はアーキテクチャに波及する([04-design.md](04-design.md) §3.2の対応ラダー)
6. **仕様変更要求への対応順位**: **①削除 > ②延期 > ③制約追加 > ④設計追加**。過去のレビュー対応は④に偏り、過剰設計の指摘に対して設計を詳細化する結果を招いた
7. **漸進的な高度化**: コンテキスト構築は「単純な切り捨て(truncation)」から始め、実使用で不足を感じてから「選抜(selection)」へ高度化する。最初から完璧なアルゴリズムを目指さない

## 2. MVP(最初の2週間)

「AIとやり取りしながら小説を書ける最小の形」。以下の**4要素+2つの安全網**のみ:

| # | 要素 | 対応要件(最小形) |
|---|---|---|
| 1 | React+CodeMirror 6でプロジェクトフォルダのファイルを開いて編集・保存できるエディタ(**Week 1にPoC#1を兼ねる**) | M-01最小 |
| 2 | 左サイドバー: `manuscript/`・`codex/` のファイルツリー表示と新規作成 | M-01/M-02最小 |
| 3 | Rust側: aho-corasickによる本文中のcodex名(+別名)の単純ハイライトとジャンプ | M-02言及検出の骨格 |
| 4 | 右サイドバー: 対象本文+一致したcodex+ユーザーが手動追加した設定をプロンプトに埋めてLM Studioへ送る単体チャット(送信内容は事前に一覧表示) | M-07+M-03の骨格 |
| 5 | **保存時に1世代バックアップコピー** | M-01。「壊れるのが怖い」でドッグフーディングが止まるのを防ぐ |
| 6 | **開いているファイル内の検索(Ctrl+F相当)** | M-01。「あのシーンどこだっけ」で止まるのを防ぐ |

**MVPで作らないもの**(明示): AI実行エンジン・共通化の一般化、コンテキストの優先順位/予算/縮退アルゴリズム、M-09自動抽出、M-04/M-05の本実装、指摘の永続アンカー、版管理UI(S-11)、FTS5全文検索、ゴールデンセット(N-06)、相関図、縦書きプレビュー、オンボーディング、リアルタイムファイル監視

**MVP完了条件**: 開発者自身がMVP上で**1万字以上執筆**し、「AI相談+設定参照」の体験メモ(効く点・効かない点)を残すこと。この実感がM2以降の優先順位を最終決定する

## 5. 将来の設計メモ(V1では実装しない)

以下は「その時が来たらこう考える」というメモであり、**現時点の実装対象ではない。ここに書かれていることを前提に実装を組んではならない。**

### 5.1 コンテキスト選抜の高度化(必要性が実感できてから)

- 選抜ソースの追加候補: 明示リンク経由、ユーザーによるピン留めの永続化
- 長文時の縮退: 全文→synopsis→frontmatterのみ、の段階化
- 前後シーンの供給(V1は渡さない)
- 参考: NovelAI Lorebookのキーワード発火、Novelcrafter Codexの自動選抜([01-survey.md](01-survey.md) §4)。Story Bible型(全部常時渡す)は採らない方針は維持

### 5.2 作品全体レビュー(V1.5以降)

- 二段要約(章要約→統合)は伏線等の情報損失が大きいため、**章ごとのレビュー結果を統合する方式**を第一候補とする
- 実行前に規模・推定トークン量・概算コストを提示して確認を取る(ローカルで数十分、クラウドで1回数ドルに達しうる)
- **要約のバックグラウンド自動生成は行わない**(保存のたびにAI処理が走る、失敗時の扱い、原稿がクラウドへ自動送信される危険=N-03違反、要約の陳腐化)。実装時点ではユーザー記入のsynopsisを主とし、明示的な操作での要約生成を検討する

### 5.3 AI品質評価(M2以降)

- ゴールデンセット(誤字・表記ゆれ・矛盾を埋め込んだテスト原稿+codex)による検出率・誤検知率の機械計測。**V1では作らず、PoC#7で誤字10件程度の最小版から始める**
- 指摘の採否をローカル記録し採択率を見る(外部送信しない)
- 品質変動の原因切り分けは、AI呼び出しログ(プロンプト実体・モデル・渡した素材)が残っていれば後から追跡できる

### 5.4 共通化・拡張の考え方

- **機能ごとに独立実装し、同じコードが2回以上必要になった時点で共通部を抽出する**。現時点の共通化候補はAI送信処理とファイル読み込み処理の2つのみ
- 「全AI機能を貫く共通パイプライン」は、AI機能を2つ以上実装した後に実際の重複を見てから定義する(先に枠を作らない)
- C-01(AI本文執筆)解禁時も、原則「AI出力は原稿へ直接書き込まない・ideas/へ保存し人間が反映」は維持する

## 5.4 ドッグフーディングの結果(M1ゲート)

**判定: 通過**(2026-07-26)。実執筆を通して機能不全は出ず、最終報告は「新たな報告事項なし」。

出た指摘と対応(すべて実装済み):

| # | 指摘 | 対応 |
|---|---|---|
| 1 | codex作成時に記入項目の雛形が欲しい | ジャンル別テンプレート(設定フォルダー内のMarkdown・ユーザー編集可) |
| 2 | **保存を忘れて編集内容が消える** | 自動保存(入力停止/切替/フォーカス喪失/ウィンドウを閉じる時)+保存状態チップ。**データ損失のため最優先で対応** |
| 3 | ペイン幅を変えたい / 右ペインを常時開かせないで | 境界のドラッグでリサイズ(幅を記憶)+右ペインの開閉(Ctrl+\) |
| 4 | 設定を見ながら書きたい(右ペインをAI専用にしない) | 「AI相談 / 参照」のタブ化。本文の設定名をCtrl+クリックで引ける |
| 5 | 項目を削除する手段がない | 項目メニュー(削除・改名・複製・エクスプローラーで表示)。**削除はゴミ箱方式**+確認ダイアログ |
| 6 | 行番号・ルーラー・任意字数の折り返しが欲しい | 実装(全角1文字の送り幅を実測して桁を出す) |
| 7 | 検索パネルが小さく操作しづらい | 他のボタンと同寸法に調整 |

**この結果から言えること**: 執筆の土台(編集・保存・参照)は成立した。**一方、M-04(校正)・M-05(レビュー)といった「編集者」の中核はまだ無い**ため、製品の差別化はこれから検証する段階にある。

#### 実使用で見つかった穴: 「形式を守らない応答」を指摘なしと誤報告していた(2026-07-31 修正)

gpt-oss-20b でレビューしたところ、**英語の散文**が返ってきた。JSONでもなく、
本文を読んだ形跡もない(小説ではなく「利用者の文章」を評していた)。

問題は出力そのものではなく**アプリの扱い**にあった。JSONとして解析できないので
`parse` が空を返し、画面には「**指摘は挙がりませんでした**」と出る。
中身のある応答が返っているのに「問題なし」と報告する — 校正で潰したはずの
**最悪の誤報告**が、形を変えてレビューに残っていた。

| 修正 | 内容 |
|---|---|
| 区別を作った | `ParsedReview::structured`。**「読み取れて指摘0件」と「読み取れなかった」を分ける**。空の一覧が返れば前者で正しい |
| 捨てない | 読み取れなかった応答は**生のまま講評欄に出す**(2,000字で打ち切り、切ったことは明示)。経路B(寛容パース)の最後の受け皿にあたる |
| 見た目を変えた | 生の応答は講評と**同じ顔で並べない**。引用の照合を通っていないため確度が違う |
| 警告 | 「**『指摘なし』ではありません**。照合できていないので鵜呑みにしないでください」 |
| 校正にも同じ穴 | `proofread::looks_structured` を追加し、同様に警告する。M-04でも「誤りなし」と誤報告しうる状態だった |
| プロンプト | システムプロンプトに**日本語で書くこと**と**前置き・箇条書きを付けないこと**を追加 |

**モデルの評価**: gpt-oss-20b は**レビューに使えない**。形式を守らず、実行のたびに
LM Studio がエンジンエラー(`peg-native format`)を返すこともあった。
04-design §8.1 の「レビューはローカル △〜×」という見立ての実例にあたる。

#### ドッグフーディングの結果(2026-07-31)

| 観察 | 対応 |
|---|---|
| **検閲ありモデル(gemma-4-12b-qat)でもレビューは成立した**。拒否されなかった | §5.9-B の未検証項目が実機で埋まった。**検閲を理由にレビューをローカル非検閲へ限定する必要はない** |
| 既定のコンテキスト長(8,192)では不足してエラーになり、**アプリがその旨を表示した** | 打ち切り検出と警告が実使用で機能することを確認。32,000へ変更したら問題なく通った |
| **レビューの質を求めるほど推論能力の高い=遅いモデルになり、タイムアウトが多発した** | **応答待ちの上限を180→240秒へ延長**(`ai::TIMEOUT_SECS`)。レビューは1回の結果が成果物なので、待てば得られるものを時間切れで捨てる損失が大きい |

**運用上の指針**(M-08へ引き継ぐ): 上の 8,192 → 32,000 は**この環境・この本文での実測**であって、
推奨値ではない。必要なコンテキスト長は本文の長さとモデルで変わり、上げすぎれば
VRAMを無駄に食って遅くなる。並列数も既定の4で足りる場合がある。
**数値を決め打ちせず、症状から当てる形で案内する**:

| 症状 | 試すこと |
|---|---|
| 打ち切りの警告が出る・応答が返らない | コンテキスト長を増やす / 1回に送る字数を減らす |
| 応答が遅い・時間切れになる | 並列数を下げる / 軽いモデルに替える(コンテキスト長は並列数の分だけVRAMを使う。§7.2) |

## 5.14 検討の入口: 設定の変化をどう扱うか(未着手)

**2026-08-01 のドッグフーディングで出た。まだ方式を決めていない。**
ここは結論ではなく「何を決める必要があるか」の控えである。

### 課題

codexに登録済みの項目が、**物語の進行とともに変わる**ことがある。

- 結婚して姓が変わる(佐藤架純 → 五十嵐架純)
- 肩書・所属が変わる、外見が変わる(「第3章以降は隻腕」)

現在のM-09は「**未登録の**固有名詞を候補として出す」だけなので、
「五十嵐架純」は**別人の新規候補**として出てくる。名寄せ(§5.12)は同一だと
本文から読み取れる場合に繋ぐ仕組みなので、章をまたぐ変化には届かない。

### 決めていない論点

1. **別名として足すのか、時点つきの情報として持つのか。**
   別名で足せば言及検出と表記ゆれ検出はすぐ通るが、**「いつから」が失われる**。
   時点つきはS-06(progression)の領域で、V1.5以降の話になる
2. **抽出が既存エントリへの追加を提案してよいか。** 名寄せで
   「既存エントリへの別名追加」を提案する経路は**実装済み**なので、
   姓の変化もそこに乗せられる可能性がある。別扱いが要るかは未検討
3. **機械が「同じ人物だ」と判断してよいか。** 同姓の別人と区別できない場合、
   勝手に統合すると設定が壊れて回復が難しい(§5.12と同じ結論になるはず)
4. **手動のみで割り切る**選択もある。頻度が低ければUIを足す価値がない

### 判断に要るもの

**ドッグフーディングでの頻度**。実際に何回起きるかが分からないうちは、
どこまで作るべきか決められない。まず起きた回数を数えるところから。

## 5.16 シーンの自動分割(2026-08-03 実装)

§5.9-D の実装。ドッグフーディングで「必要度が高い」と評価された項目。

### 形

項目メニュー →「シーンに分割…」→ 切れ目の候補を出す → **前後を並べて見せる** →
採用したものだけ適用。押すまで何も起きない。

**前後を並べる**のが要点。前の場面の終わりと次の場面の始まりが並んでいないと、
そこで切ってよいかは判断できない。見出しはその場で直せる
(AIの付けた名前をそのまま使わせない)。

### 守ったこと

| | |
|---|---|
| **本文を1文字も変えない** | AIがするのは「どこで切るか」の提案だけ。分割後を連結すると元に戻ることをテストで固定した(C-01の境界=06 §2-1) |
| **提案型** | 既定は全部オンだが、外せる。1つも選ばなければ実行できない |
| **元を消さない** | 分割後、元ファイルは**ゴミ箱へ退避**(削除と同じ流儀)。戻せるからこそ試す気になる |
| **位置を保存しない**(D-7) | 適用時に**引用から引き直す**。提案を見てから本文が変わっていたら、ずれた位置で切らずに**失敗させる** |
| **半端な状態を作らない** | 書き込み先が全部空いているか先に確かめる。1つでも衝突したら何も作らない |
| **切れ端を作らない** | 200字未満の断片になる切れ目は落とす。行頭へ寄せて段落の途中で切らない |

### 分かったこと

- **分割送信はしない。** 校正やレビューは分けて送れるが、切れ目は**全体を通して
  読まないと分からない**。長すぎる原稿は打ち切りとして正直に伝える
- ファイル名は機械的に連番(`01-転校初日-1.md`)、**見出しはフロントマターの title**
  に置く。見出しをファイル名にすると衝突や使えない文字の問題が出る。
  ツリーには title が出るので見た目は損なわれない
- 引用の位置解決が**3箇所目**(レビュー・分割)になったので `mentions::locate_quote`
  へ出した。「同じコードが2回以上必要になってから共通化する」の条件を満たしたため

## 5.12 検討: 抽出の名寄せ(2026-07-31 実装済み)

### 課題
「黒木龍一(肩書=教授、愛称=りゅーちゃん)」は、本文では **黒木龍一 / 黒木 / 龍一 / 教授 /
りゅーちゃん** と複数の呼び名で現れる。これらは1人の人物であり、codexでは
`黒木龍一.md` 1件に集約され、残りは `aliases` に入るべきである。

**現状は集約しない。** M-09は名前ごとに独立した候補を出すため、5件のエントリが提案される。
これは単にノイズなだけでなく、**下流を壊す**:
- 言及検出(M-02)が「黒木」を別人として扱う
- 表記ゆれ検出(M-04-02)の登録名が増え、誤検出の温床になる
- 「教授」のような一般語が正式名として登録されると実害が大きい

### 方式の検討

| 方式 | 「黒木」「龍一」 | 「教授」「りゅーちゃん」 | 評価 |
|---|---|---|---|
| 部分文字列(姓・名は全名の一部) | **拾える** | **拾えない** | 機械的で確実だが守備範囲が狭い。`青葉` ⊂ `青葉高校` のような別物も繋いでしまう |
| 共起・文脈の統計 | 一部 | 一部 | 実装量が大きい割に精度が読めない |
| **LLMに別名ごと抽出させる** | **拾える** | **拾える** | **推奨**。「誰が誰か」は解釈であり、機械には原理的に無理。LLMの得意分野 |

**採る方針**: 抽出の1回のリクエストで**正式名と別名をまとめて出させる**。
呼び名の対応づけは本文を読まないと分からない解釈であり、ここはLLMに任せるのが正しい。
ただし**検証は機械側**で行う(06 §2-5 の原則そのまま: 解釈はLLM、照合は機械)。

### 設計案

**1. 出力形式を変える**(プロンプトとパースのみの変更。追加のリクエストは発生しない)

```json
{"entities":[{"name":"黒木龍一","kind":"character","description":"…",
              "aliases":["黒木","龍一","教授","りゅーちゃん"]}]}
```

**2. 機械側の検証(追加する規則)**

- 別名も**本文に実在すること**を確認する(幻覚の除去。正式名と同じ扱い)
- **別名の判定は正式名より緩くする**。`looks_like_proper_noun` はひらがなを弾くが、
  **あだ名はひらがなが普通**(りゅーちゃん)。別名は「2文字以上・除外語でない」だけを課す
- 別名が**他の候補の正式名と衝突**する場合、独立候補の方を落として別名に寄せる
  (「教授」が単独候補としても挙がったら、黒木龍一の別名として扱う)
- 同じ別名が**複数の正式名に付く**場合は、どちらにも付けずユーザーへ提示する
  (作中に教授が2人いる場合など。機械が勝手に決めない)
- 1文字の別名は却下(言及検出が誤爆する)

**3. 既存codexとの照合を強化する**(現状は完全一致のみ)

いま `verify` は候補名が既存の正式名・別名と**完全一致**する場合だけ除外している。
名寄せを入れるなら、**既存エントリへの別名追加**も提案できるべき:

- 候補の別名群に既存エントリの名前が含まれる → その候補は**既存エントリと同一**
  → 「新規作成」ではなく「**既存の『黒木龍一』に別名を追加**」として提案する
- これがないと、codexが育つほど「既に居る人物の断片」が新規候補として出続ける

**4. 既存ファイルへの別名追加をどう書くか(要注意)**

[03-data-format.md](03-data-format.md) は「アプリはフロントマターを再シリアライズしない」
ことで未知フィールドの保全を担保している。別名追加はこの原則に触れる。

→ **`aliases:` の行だけを外科的に書き換える**方式にする。他の行はバイト単位で温存する。
`aliases` 行が無ければ `title` の直後に挿入する。全体を読み書きし直さないこと。

**5. UI**

- 候補を「正式名+別名」のまとまりで表示し、**別名ごとに個別に採否**できる
- 提案の種類を区別する: **新規エントリ(別名つき)** / **既存エントリへの別名追加**
- 一般的すぎる別名(「教授」「先生」)には注意を促す。**別名は言及検出と表記ゆれ検出に
  直接効く**ため、誤った別名は校正の誤検出を生む

### 自動化の範囲(P-8との整合)
名寄せは「気づくこと」なので自動でよい。**「決めること」(このcodexに統合する)は
ユーザーが持つ**。同姓・同肩書の別人を機械が勝手に統合すると、設定が壊れて回復が難しい。

### 実装順
1. プロンプトとスキーマに `aliases` を足す(小さい)
2. 機械側の検証規則を追加(テストしやすい純粋関数)
3. 既存codexとの照合強化 → 「別名追加」提案
4. `aliases:` 行の外科的な書き換え
5. UI(まとまり表示・別名ごとの採否)

1〜2だけでも「5件のゴミ候補」が「1件の候補+別名4つ」になり、効果は大きい。

## 5.7 検討: AI相談の会話コンテキスト(未実装)

### 現状
`ask_ai` が組み立てるのは毎回 `[system, user(本文+設定+依頼)]` の1往復のみで、過去のやりとりを一切持たない。
利点は明確で、**コストが読める・毎回の入力が完全に見える(U-05)・ローカルLLMの短いコンテキストに収まる**。
欠点も明確で、「じゃあ2案目をもっと詳しく」「さっきの指摘を別の言い方で」が言えず、毎回すべて書き直すことになる。

### 一律に決めない、が結論の方向

用途によって必要性が正反対なので、**全機能に一律で会話を付ける/付けない、のどちらも誤り**と考える。

| 用途 | 会話の必要性 | 理由 |
|---|---|---|
| M-03 アイデア出し・設定の深掘り | **高い** | 発想→絞り込み→深掘りは本質的に往復。ドッグフーディングで「印象が良い」とされたのもこの用途 |
| S-10 執筆前ブリーフィング | 中 | 打ち合わせ的な性質があり往復が活きる |
| M-04 校正 / M-05 レビュー | **低い(むしろ不要)** | 対象範囲に対する一回の判定が成果物。履歴はノイズとコストにしかならない |

→ **会話モードをユーザーが明示的にオン/オフする**形が素直。既定はオフ(現状維持)。

### 過去コンテキストの保存方法(要検討の中心)

| 案 | 内容 | 評価 |
|---|---|---|
| **A. メモリのみ(セッション中だけ)** | アプリを閉じると消える。残したいやりとりは「この相談を残す」で `ideas/` へMarkdown保存 | **推奨**。会話は原稿ではなく過程の副産物であり、正本(D-1)に自動で混ぜない。02 §1.1「AI出力はメタテキスト、原稿への反映は人間の手」と一貫する。未決-5(reviews/の保存粒度)と同じ判断 |
| B. `.app/chats/<日時>.md` に自動保存し再開可能にする | 続きから相談できる | 会話の再開という機能が要る割に、翌日その会話を続けたい場面が本当にあるか未検証。ゴミが溜まる |
| C. `ideas/` へ全部自動保存 | 人間可読・正本内 | 採用していない案まで正本を汚す。明確に不可 |
| D. 既存の `.app/logs/` を流用 | 実装ゼロ | 追記型の呼び出しログであり会話の再構成には向かない。用途が違う |

### コンテキストの送り方(未決)
- 本文+codexを**毎回送るか、初回だけ送るか**。毎回送ると往復ごとに数千字が積み上がりローカルLLMの上限に早く当たる。初回だけにすると、途中で本文を書き足した分がAIに見えない
- 折衷案: **本文ハッシュが変わったら再送**([04-design.md](04-design.md) §6.4で確立した鮮度管理の考え方を流用できる)
- 履歴が予算を超えたときは**古い往復から単純に落とす**。要約による圧縮は行わない(§5.1・開発原則7の漸進方針。要約は情報損失と追加コストを生む)
- 往復数または文字数の上限を決め、超えたら「新しい相談を始める」を促す

### 再導入してはいけないもの(注意)
会話履歴の管理は、撤回済みの設計を裏口から呼び戻しやすい。[06-decision-log.md](06-decision-log.md) §4 で撤回した **入力ハッシュキャッシュ / コンテキストの優先順位・予算計算・段階的縮退 / 要約のバックグラウンド生成** を、履歴管理の名目で復活させないこと。V1で許すのは「単純に古いものから落とす」までとする。

### 「対応しない」と割り切る場合
代替手段は「前回のやりとりを自分で依頼欄に貼る」で、これは現状そのもの。M-03が主用途である以上、負荷は残り続ける。
既存ツール(Novelcrafter・Sudowrite)もチャット形式を持つため、**長期的には非対応は弱い**と判断する。ただし着手はM2以降で足りる。

| C. 対応表をユーザーが編集できる | Aの拡張 | 表記の好みは分かれる(「設定」か「資料」か等)ので将来は欲しい。ただし初手には過剰 |

### 推奨する実装(案A)

| codex/items | 物品 |
| codex/terms | 用語 |
| codex/notes | メモ |
| plot | プロット |
| ideas | 着想 |
| reviews | 講評 |

- 対応表は**プロジェクト直下の既定フォルダーにだけ**適用する。ユーザーが自分で掘ったサブフォルダー(`characters/主要/` 等)はそのまま出す(既に日本語で付けられるため)
- 実体のパスは変えないので、ツールチップやステータス表示には実パスを出し、**ディスク上の名前を隠さない**
- 案Bへ移行するときは、この対応表がそのまま改名の対応表として使える

### 判断が要る点
案Aは「UIとディスクの表記が食い違う」ことを受け入れる。P-5(人間が直接編集できる)を掲げている以上、ここは思想的な妥協になる。**目的に対して最小の手段であり、かつ可逆である**ことを理由に許容する、という整理でよいかは着手時に確認する。

### 実装結果(2026-07-26)
案Aで実装。対応表は `src/components/folderLabels.ts`。
- 置き換えたフォルダーはツールチップに実パスを出し、ディスク上の名前を隠さない
- 新規作成ダイアログと削除確認も表示名に揃えた(`設定 / 人物 に作ります`)
- ユーザーが掘ったサブフォルダーは実体名のまま。深い階層の同名(`codex/characters/characters`)も置き換えない
- あわせてフロントエンドのテスト基盤(Vitest)を導入し、対応表と言及検出の規則を固定した(15件)

# 第1部: V1で実装する範囲

## 1. AI呼び出し(薄いクライアント)

V1のAI呼び出しは**薄いクライアント1つ**とする。抽象化層・エンジン・プロファイル解決機構は作らない。

```
AiClient
  send(request) -> response        // 単発呼び出し
  stream(request) -> event stream  // SSEストリーミング(T-03)
  cancel()                         // 実行中の中断
```

- 実体はuggg流用のOpenAI互換クライアント([04-uggg-reuse-notes.md](04-uggg-reuse-notes.md))+SSE追加
- 接続先(Base URL・APIキー・モデル名)は設定画面の値をそのまま渡す。機能別の自動モデル解決はしない(ユーザーが設定した1つの接続先を使う)
- リトライはHTTPクライアント層の薄いラッパーで扱う(タイムアウト・一時エラーの単純再試行のみ)
- **プロンプトの組み立ては各機能側に置く**。共通テンプレート機構は作らない
- ログ(T-06): 送信プロンプト全文・応答全文・モデル名・トークン数・所要時間を `.app/` に追記保存する。プロンプトのバージョン管理機構は持たず、**プロンプト実体をログに残す**ことで後から比較可能にする

**V1で作らないもの(撤回)**: 入力ハッシュによる応答キャッシュ(温度・モデル・プロンプト・接続先が異なれば意味が変わるため、キーと無効化条件が膨らみ誤再利用の危険がある)、レート制御(ローカル・単一ユーザーでは不要)、複数モデルの多重化、評価実験用の抽象化。

## 2. コンテキスト構築(V1は3系統のみ)

AIへ渡すのは次の3つだけ。優先順位アルゴリズム・トークン予算計算・段階的縮退・importance・関係グラフ辿りは**V1では実装しない**。

| # | 素材 | 取得方法 |
|---|---|---|
| 1 | 対象本文(現在のシーン/選択範囲) | そのまま |
| 2 | 対象本文中で名前・別名が一致したcodexエントリ | 言及検出(aho-corasick)。多すぎる場合は**単純に上限件数で切る(truncation)** |
| 3 | ユーザーが明示的に追加したcodexエントリ・プロット | UIで選択 |

- 長さ超過時の扱いは**単純な切り捨て**から始める。素材の重み付け・縮退への高度化は、実使用で不足を感じてから段階的に行う(R3の漸進アプローチ)
- **透明性(U-05)**: 実行前に「何を渡すか」の一覧を表示し、その場で外せること。V1で必要なのはこれだけ(構築ログの詳細分析は不要)
- 関係グラフを1段辿る自動選抜は**採らない**(主人公→所属→王国→女王 のように無関係なエントリが混入する)。静的重要度(importance)も採らない(「常に重要」と「この場面で重要」は別概念であり、選抜精度が上がる保証がない)

## 3. 出力の受け取り(二経路)

| 経路 | 用途 |
|---|---|
| A: `response_format.json_schema` | 校正指摘・設定抽出など構造が固い出力 |
| B: プレーンテキスト+緩い出力規約+寛容パース | レビュー講評・ブレストなど自然文が主の出力、および小型モデル |

- Aは失敗時にBへフォールバック(uggg流用の `extract_json_blob` を使用)
- 経路はコード上で機能ごとに直接指定する(設定による動的切替機構は作らない)
- スキーマ強制による日本語品質・速度への副作用はPoC#3([05-tech-selection.md](05-tech-selection.md))で計測し、悪ければBを既定にする

## 4. 提示と鮮度管理(アンカーの簡素化)

**V1では個別指摘の永続再アンカーを行わない**(段落インデックス・曖昧一致・失効管理の自作を撤回)。

1. 文字オフセットは保存しない([03-data-format.md](03-data-format.md) D-7)
2. **校正・レビューの結果は「実行時点の本文ハッシュ」とともに保持する。本文が変わったら結果全体を『古い結果』として表示し、再実行を促す**
3. 表示中の指摘を本文に対応付ける必要がある場合は、**引用文字列の単純検索**(完全一致→部分一致)で足りる範囲に留める。複数ヒット時は先頭を採用し、見つからなければその指摘は「位置不明」と表示する
4. 言及ハイライトはメモリ上でオンデマンド算出(aho-corasick)
5. 執筆中は原則ハイライトを載せず、校正・レビュー時のみ表示する(U-10のモード分離。エディタ側のリスク低減=[05-tech-selection.md](05-tech-selection.md) §3.2)

# 第2部: 将来の設計メモ(V1では実装しない)

以下は「その時が来たらこう考える」というメモであり、**現時点の実装対象ではない。ここに書かれていることを前提に実装を組んではならない。**

## 5. コンテキスト選抜の高度化(必要性が実感できてから)

- 選抜ソースの追加候補: 明示リンク経由、ユーザーによるピン留めの永続化
- 長文時の縮退: 全文→synopsis→frontmatterのみ、の段階化
- 前後シーンの供給(V1は渡さない)
- 参考: NovelAI Lorebookのキーワード発火、Novelcrafter Codexの自動選抜(01調査§4)。Story Bible型(全部常時渡す)は採らない方針は維持

## 6. 作品全体レビュー(V1.5以降)

- 二段要約(章要約→統合)は伏線等の情報損失が大きいため、**章ごとのレビュー結果を統合する方式**を第一候補とする
- 実行前に規模・推定トークン量・概算コストを提示して確認を取る(ローカルで数十分、クラウドで1回数ドルに達しうるため)
- **要約のバックグラウンド自動生成は行わない**(保存のたびにAI処理が走る、失敗時の扱い、原稿がクラウドへ自動送信される危険=N-03違反、要約の陳腐化など副作用が大きい)。全体レビューを実装する時点で、ユーザー記入のsynopsisを主とし、明示的な操作での要約生成を検討する

## 7. 機能とモデル能力の対応(初期仮説・プリセット候補)

**要求仕様ではなく参考値**。モデル性能は短期で変わるため、実装では設定ファイルとして持ち、実測で改訂する。V1は「ユーザーが設定した1接続先を使う」だけであり、機能別の自動割当は行わない。

| 機能 | ローカル(7B-14B級) | クラウド | 備考 |
|---|---|---|---|
| ブレスト・アイデア出し | ○ | ◎ | 精度要求が低くローカル向き |
| 誤字脱字検出 | △ 要検証 | ◎ | PoC#7で実測 |
| 表記ゆれ検出 | ○(補助のみ) | ◎ | **機械照合(aho-corasick)が主、LLMは解釈補助** |
| レビュー(シーン/章) | △〜× | ◎ | 中間情報の無視傾向 |
| 全体レビュー | × | ◎ | V1.5 |
| 設定抽出 | ○ 見込み | ◎ | 固有名詞フィルタが前提 |
| 整合性チェック | × | ○ | V1.5以降 |

- レビューは将来「軽量モード(ローカル向け)/標準モード(クラウド推奨)」に分ける案がある(接続モデルによる期待値の差をUIで明示する目的)

## 8. AI品質評価(M2以降)

- ゴールデンセット(誤字・表記ゆれ・矛盾を埋め込んだテスト原稿+codex)による検出率・誤検知率の機械計測。**V1では作らず、PoC#7で誤字10件程度の最小版から始める**
- 指摘の採否をローカル記録し採択率を見る(外部送信しない)
- 品質変動の原因切り分けは、§1のログ(プロンプト実体・モデル・渡した素材)が残っていれば後から追跡できる

## 9. 共通化・拡張の考え方

- **機能ごとに独立実装し、同じコードが2回以上必要になった時点で共通部を抽出する**。現時点の共通化候補はAI送信処理とファイル読み込み処理の2つのみ
- 「全AI機能を貫く共通パイプライン」は、AI機能を2つ以上実装した後に、実際の重複を見てから定義する(先に枠を作らない)
- C-01(AI本文執筆)解禁時も、原則「AI出力は原稿へ直接書き込まない・ideas/へ保存し人間が反映」は維持する

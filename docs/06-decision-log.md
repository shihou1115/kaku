## 2. 確定した原則(再議しない)

| # | 原則 | 根拠 |
|---|---|---|
| 1 | **AIは本文を書かない**。AI出力はメタテキスト(案・要約・質問・指摘)に限り、原稿ファイルへ直接挿入する機能を持たない | ユーザーのプロダクト定義。第1回R3の「素材提供では価値不足」という生成寄りへの誘導は**不採用**(§5) |
| 2 | **AIの4役割**(アイデア出し/設定管理/誤字脱字/レビュー)をV1要求に含める | ユーザー決定。第3回の「V1仮説を1つに絞れ」はQ-7として提示し、**2026-07-25に現状追認で確定** |
| 3 | **ファイルが正、アプリは従**。索引は再生成可能 | P-5。[03-data-format.md](03-data-format.md) D-1 |
| 4 | **文字オフセットを永続化しない** | 外部編集で位置は常に無効化されうる。D-7 |
| 5 | **機械照合が主、LLMは解釈補助**(表記ゆれ・言及検出) | 精度と再現性。aho-corasickで足りるものにLLMを使わない |
| 6 | **AIは非破壊**。指摘・提案は常に採否をユーザーに委ね、勝手に書き換えない | 「編集者」コンセプトの体現。U-06 |
| 7 | **codexの種別は開放語彙**(推奨5種+ユーザー定義)。種別のハードコード増殖はしない | World Anvilの過剰機能化を反面教師とする |
| 8 | **設定自動抽出(M-09)はMustだが提案型・手動実行のみ** | コールドスタート解消に必須(§3)。ただしローカルLLMのNER精度ではノイズ地獄になるため常時自動抽出はしない |
| 9 | **外部編集できること ≠ 同時編集を安全に統合できること**。V1は前者のみ保証 | 後者はローカルアプリ内に同期・競合解決システムを抱えることになる |
| 10 | **共通化は同じコードが2回以上必要になってから** | 実装前の抽象化が3回目のレビューで最大の問題と指摘された |

## 4. 一度採用し、後に撤回した設計(**再追加しないための記録**)

第2回で追加し、第3回で撤回したもの。**「良い設計だから入れよう」と再提案されやすいため、撤回理由を明記する。**

| 撤回したもの | 撤回理由 |
|---|---|
| **汎用AI実行エンジン**(プロンプトバージョン管理・モデル自動解決・リトライ/フォールバック・レート制御・キャッシュ・使用量記録を集約) | 有効なプロンプトが2〜3個しか固まっていない段階での抽象化。V1は `send/stream/cancel`+ログの薄いクライアントで足る |
| **入力ハッシュによる応答キャッシュ** | 同一入力でも温度・モデル・プロンプト・system prompt・接続先・アプリバージョンが違えば結果の意味が異なる。正しく作るとキーと無効化条件が膨らみ、省略すると誤った応答を再利用する |
| **レート制御・複数モデル多重化・評価実験用の抽象化** | ローカル・単一ユーザーでは不要。必要性が実利用から得られていない |
| **プロンプトバージョン管理機構** | プロンプト実体をログに残せば後から比較できる。レジストリは不要 |
| **機能別モデル割当(プロファイル)機構** | V1は「設定した1接続先を全機能で使う」で足る |
| **コンテキストの優先順位表・トークン予算計算・段階的縮退** | 成熟RAG相当の設計。V1で扱うのは「対象本文+名前一致codex+手動追加」だけであり差が大きすぎる。単純な切り捨てから始める |
| **importance(main/sub/minor)による選抜** | 「常に重要」と「この場面で重要」は別概念。静的重要度を入れても選抜精度が上がる保証がなく、ユーザーに管理作業を増やす |
| **relationsを1段辿る周辺エントリの自動選抜** | 主人公→所属→王国→女王 のように、現在の場面に無関係なエントリが大量に混入する |
| **機能別コンテキストポリシー表**(段階×機能の分岐表) | 分岐を減らすための抽象化が設定分岐を増やしていた。機能ごとに独立実装する |
| **段落インデックス+曖昧一致+失効管理による指摘の永続再アンカー** | 段落インデックス自体が外部編集でズレる。本文ハッシュで「古い結果」と表示する方式で必要十分 |
| **要約のバックグラウンド自動生成・キャッシュ** | 保存ごとにAI処理が走る。失敗時の扱い・陳腐化に加え、**原稿がクラウドへ自動送信されうる(N-03違反)** |
| **リアルタイムファイル監視・競合の自動退避・低優先の全体再索引** | 外部同時編集対応への膨張。フォーカス復帰時の確認+再読込促しで足る |
| **N-01の性能数値をV1の合格条件とすること** | 未実測の数値がアーキテクチャを不必要に誘導する。参考値へ格下げし、V1判定は「入力が遅延しない/切替が妨げにならない/1万字で動く」 |

## 5. 却下・保留した提案

| 提案 | 判定 | 理由 |
|---|---|---|
| 「編集者特化では価値不足」→本文生成寄りへ | **不採用** | 「AIは書かない」はユーザーの明示的決定。価値不足リスクへの回答は生成ではなくM-09(外部記憶が育つ)・S-10(執筆前ブリーフィング)・全体構成編集で行う |
| V1要求を単一仮説(設定を引き当ててAI相談できるエディタ)へ縮小 | **保留→現状追認** | プロダクト定義に関わるためQ-7としてユーザー判断に委ね、2026-07-25に現状維持で確定。MVPの作業内容はどちらでも同じ |
| M-03〜M-09を「確定要求」から仮説バックログへ降格 | **一部採用** | M-06のみ降格。4役割の要件は維持し、実装順(M1→M3)で過剰投資を防ぐ |
| 要求IDの全面再採番(粒度統一のため) | **不採用**(元の指摘「要件粒度が不揃い」自体は一部採用) | 文書間の参照安定性を優先。太い要件のサブ分解(M-04-01〜04)で対応 |
| codexの種別を多数ハードコードで用意(組織・魔法・歴史…) | **一部採用** | 開放語彙化で対応。種別ごとの専用UIは作らない |
| 集約ファイル形式(1ファイルに複数エントリ) | **見送り** | 1概念1ファイル原則(OKF互換)を崩しパーサも複雑化する。サブフォルダ+UIグルーピングで代替([03-data-format.md](03-data-format.md) 未決-6) |
| 「json_schema強制で日本語が不自然化・速度低下が多発する」という事実認定 | **未検証扱い** | 発生し得る副作用として妥当だが定量的根拠は提示されていない。PoC#3の計測項目とし、回避経路(B経路)を先に用意 |

## 6. 前提が変わったことによる再検討(2026-07-26)

§4は「一度採用して撤回した設計」であり、**再提案しないための記録**である。
一方、**撤回の理由そのものが成り立たなくなった場合は、再検討してよい**。
両者を取り違えないよう、ここに経緯を残す。

### 何が変わったか
- **P-7**: ローカルLLMが推奨環境になった(理由は費用ではなく、犯罪描写を扱うジャンルで
  非検閲モデルが必要なため)
- **P-8**: ツール自体の作業負荷を最小にする方針が明示された
  (理想は「自動でシーン分けと設定抽出を行い、執筆者は書くだけ」)

### 再検討の対象と、撤回理由の現状

| 撤回したもの(§4) | 当時の撤回理由 | 現状 |
|---|---|---|
| **要約のバックグラウンド自動生成** | ①保存ごとにAI処理 ②失敗時の扱い ③**原稿がクラウドへ自動送信される(N-03違反)** ④要約の陳腐化 | **③は消えた**(ローカル既定なら外部送信が無い)。①も費用面では消えたが**計算資源の占有は残る**。②④は未解決 |
| **M-09の保存時バックグラウンド提案** | ①ローカルLLMのNER精度による候補ノイズ ②承認作業が執筆を阻害 | **①は緩和された**。M-09実装で機械側の検証(固有名詞らしさ・本文実在性・登録済み判定)を入れたため。**②は設計次第**(通知を出さず、見たいときだけ見る形なら阻害しない) |
| 入力ハッシュキャッシュ / レート制御 / モデル自動解決 / 優先順位・予算・縮退 | 実装前の過剰な抽象化 | **変わらず撤回のまま**。P-7/P-8はこれらを必要としない |

### 判断
- **自動化してよいのは「気づくこと」であって「決めること」ではない**(P-8)。
  採否をユーザーが持つ限り、U-06(非破壊)とは矛盾しない
- 残る実務上の障害は**計算資源の占有**(執筆中にGPUを使うと入力が重くなりうる)と
  **失敗時の扱い**。着手時にはこの2点を設計で潰すこと
- **§4の他の項目は再検討の対象ではない**。前提が変わっていないため
